# Surat Real Estate: SQL Data Cleaning

Учебный проект: очистка "грязных" данных о недвижимости средствами SQL: дубли, пропуски, смещённые колонки, текстовые поля с валютой и единицами измерения.

## Стек
- Python (pandas): загрузка сырых данных
- PostgreSQL: хранилище и вся логика очистки

## Источник данных
[Surat Real Estate Dataset (Uncleaned) на Kaggle](https://www.kaggle.com/datasets/kunjadiyarohit/flats-uncleaned-dataset) - датасет объявлений о недвижимости с типичными проблемами качества данных

### 1. Пропуски и дубли

![Nulls and duplicates](docs/screenshots/nulls_and_duplicates_summary.png)

### 2. Смещение значений между колонками

![Column shift](docs/screenshots/column_shift_transaction_status_floor.png)

В колонках `transaction`, `status`, `floor`, `furnishing`, `facing` данные перемешаны, например, в `transaction` встречаются значения вроде "New Property", "5", "Resale", которые логически принадлежат разным полям, а в `status` размеры участков вида "110 X 27.27" вместо ожидаемого статуса сделки. Похоже, что при исходном парсинге сайта не все объявления содержали одинаковый набор характеристик, из-за чего значения сдвинулись в соседние колонки.

### 3. Несогласованные единицы измерения цены

![Price units mismatch](docs/screenshots/price_currency_units_mismatch.png)

Колонка `price` содержит два разных масштаба без явного разделения:
- **Lac** - сотни тысяч рупий (1 Lac = 100,000)
- **Cr**  - десятки миллионов (1 Cr = 10,000,000)

Например, `₹1.05 Cr` и `₹38 Lac` - визуально похожи по формату, но отличаются в 100 раз. Без преобразования к единому масштабу любая агрегация (сумма, среднее) будет некорректной. Аналогично `price_per_sqft` - текст с символом валюты, запятыми-разделителями тысяч и суффиксом "per sqft".

## Схема данных

Все поля на этапе staging хранятся как `VARCHAR`. Типизация и очистка происходят на уровне SQL, а не при загрузке, чтобы не потерять исходные "грязные" значения.
 
Полный файл - [`sql/01_create_table.sql`](sql/01_create_table.sql).

Очистка выполняется на копии исходной таблицы (`surat_cleaning`), созданной через `CREATE TABLE AS SELECT * FROM surat_uncleaned`. Все дальнейшие шаги применяются через `UPDATE`/`DELETE`/`ALTER TABLE`, а не пересозданием таблиц.
['02_create_cleaning_table.sql'](02_create_cleaning_table.sql)
 
## Обнаруженные проблемы и как они устранены
 
### 1. Дубли строк
 
**Найдено:** 109 полностью дублирующихся строк из 4525.
**Решение:** удалены через `DELETE` с оставлением записи с минимальным `row_id` в каждой группе дублей - [`sql/03_delete_duplicates.sql`](sql/03_delete_duplicates.sql). Итог: **4416** уникальных строк.
 
### 2. Числовые поля, записанные как текст
 
**`square_feet`** содержал не только "sqft", но и другие единицы измерения (`sqyrd`, `sqm`, `acre`, `ground`, `rood`), а также значения из других колонок (`Resale`, `Ready to Move` без единой цифры). Все единицы приведены к единому масштабу с соответствующими коэффициентами. Утёкшие текстовые значения помечены как `NULL`. [`sql/04_clean_square_feet.sql`](sql/04_clean_square_feet.sql)
 
**`price`** - два разных масштаба без явного разделения: **Lac** (×100,000) и **Cr / Crore** (×10,000,000), плюс значения вида "Call for Price" без цифр. Приведено к единой шкале (рупии). [`sql/05_clean_price.sql`](sql/05_clean_price.sql)
 
**`price_per_sqft`** - текст с символом валюты (₹), запятыми-разделителями тысяч и суффиксом "per sqft". Извлечено чистое число. [`sql/06_clean_price_per_sqft.sql`](sql/06_clean_price_per_sqft.sql)
 
### 3. Проверка согласованности цены
 
Гипотеза: `price = square_feet × price_per_sqft`. Проверка показала:
- У подавляющего большинства объявлений расхождение укладывается в разумный разброс
- Обнаружены единичные объявления с экстремальным расхождением (сотни–тысячи процентов, например одно из 1 BHK-объявлений отличается от расчётной цены на **11565%**). Вероятно, ошибки ввода цены или площади в исходном объявлении
- Решение: такие строки **оставлены как есть** (не удалены и не изменены), поскольку невозможно достоверно определить, какое из трёх чисел ошибочно, без обращения к первоисточнику.
 
[`sql/07_check_price_consistency.sql`](sql/07_check_price_consistency.sql), скриншот: [`docs/screenshots/price_consistency_outliers.png`](docs/screenshots/price_consistency_outliers.png)
 
### 4. Смещение значений между колонками
 
В `transaction`, `status`, `floor`, `furnishing`, `facing` обнаружено смещение - значения одного смыслового поля периодически оказываются в другой колонке (например, "Furnished" в `transaction`, "5 out of 13" в `status`).
 
**Восстановлены полностью:**
- **`transaction_clean`** - поиск значений "Resale" / "New Property" по всем пяти колонкам, а не только по `transaction`
[`sql/07_clean_transaction.sql`](sql/08_clean_transaction.sql)
- **`status_clean`** - аналогичный поиск по шаблону "Ready to Move" / "Poss. by ..."
[`sql/08_clean_status.sql`](sql/09_clean_status.sql)
 
**Ограничение:** колонки `floor`, `furnishing`, `facing` также подвержены смещению, а часть значений (тип владения: Freehold / Co-operative Society / Power of Attorney; возраст постройки; размеры участка) относится к полям, которых вообще нет в исходной схеме из пяти колонок. Полное восстановление этих полей потребовало бы обращения к первоисточнику данных и выходит за рамки текущей итерации проекта.
